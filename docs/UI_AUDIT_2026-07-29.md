# UI Audit — 2026-07-29

## Scope and baseline

- Surface reviewed: desktop research cockpit and shared application shell, then the shared CSS and route-level components that inherit from it.
- Baseline route: `/` at 1440 × 900 with a connected local backend and a selected research project.
- Validation run before changes: `npm.cmd run typecheck`, `npm.cmd test` (29 tests), and `npm.cmd run build` all passed.
- The working tree already contained uncommitted changes to `frontend/src/research-map.tsx` and `frontend/src/styles/feature-pages.css`; they are deliberately excluded from this audit commit and will not be overwritten.

## Health score: 12 / 20 — usable, but the visual system is brittle

| Dimension | Score | Evidence |
| --- | ---: | --- |
| Accessibility | 3 / 4 | Semantic navigation, skip link, `aria-current`, live status, focus styles, and reduced-motion coverage are present. |
| Performance | 2 / 4 | Production CSS is 125 kB raw / 22 kB gzip and JavaScript is 394 kB raw / 117 kB gzip. The product is desktop-first, but all routes and most styling ship together. |

## Findings

### P1 — The cascade is the primary UI delivery risk

- **Location:** `frontend/src/styles/index.css`, `legacy.css`, `shell.css`, `components.css`, `responsive.css`, and feature styles.
- **Category:** Theming / maintainability.
- **Evidence:** The entry point imports `legacy.css` first and then ten further override sheets. The loaded style tree has 1,430 `!important` declarations. The same shared selectors are redefined repeatedly (`.topbar` 15 times, `.route-navigation` 15 times, `.card` 44 times, `.status` 31 times).
- **Impact:** A local page fix can silently change another route, make state styles win or lose based on import position, and force later work to add more overrides. This is why the product currently feels partly polished and partly inherited.
- **Recommendation:** Make tokens the only source for color, spacing, radius, shadow, focus and state values; add one late shared-system layer for shell/components; progressively delete or scope legacy rules instead of overriding them. Keep page CSS route-scoped.

### P1 — Navigation asks users to parse the product twice

- **Location:** `frontend/src/main.tsx` (sidebar nav and `route-navigation`), `frontend/src/styles/shell.css`.
- **Category:** Information architecture / responsive behaviour.
- **Evidence:** Every page displays both a multi-group sidebar and a nine-item feature route strip below the top bar. The cockpit also repeats several of those destinations as calls to action.
- **Impact:** Researchers in deep work must distinguish project context, global navigation, route navigation and page shortcuts before they can focus on the actual task. At a 900 px-wide desktop viewport, the second nav becomes a horizontal scroll target rather than a stable orientation aid.
- **Recommendation:** Keep the sidebar as the primary product map. Replace the global route strip with contextual page-local steps or a compact “related work” menu, only where it advances the current workflow.

### P1 — Surface hierarchy is inconsistent between shell and pages

- **Location:** shared shell and component styles; route styles in `cockpit.css`, `pages.css`, `feature-pages.css`, `workflow-settings.css`, and `run-center.css`.
- **Category:** Product UI / visual hierarchy.
- **Evidence:** The dashboard mixes elevated cards, bordered panels, pills, status chips, an extra top-level route strip, and different heading treatments. The CSS contains 122 `box-shadow` declarations and 44 separate `.card` definitions.
- **Impact:** Important research state competes with its containers. Users scan visual chrome before they scan the next research action or evidence status.
- **Recommendation:** Use a three-level surface model only: canvas, quiet section, and raised actionable surface. Reserve elevation for hover, menus, and focused work units. Give each route a single page header and one dominant next action.

### P2 — The existing token system is bypassed too often

- **Location:** all CSS sheets, especially `legacy.css` and `shell.css`.
- **Category:** Theming / accessibility.
- **Evidence:** There are 1,451 hard-coded hex colors despite `tokens.css` already defining the product palette. Multiple focus and state colors are duplicated across stylesheets.
- **Impact:** Theme refinements, contrast corrections, and status consistency need broad search-and-replace work instead of a controlled token change.
- **Recommendation:** Add semantic state and surface tokens; migrate the shell and shared components first; prohibit fresh literal colors except in token definitions.

### P2 — Initial-load work is larger than the desktop surface needs

- **Location:** `frontend/src/main.tsx`, style entry point, Vite build output.
- **Category:** Performance.
- **Evidence:** The production build emits one 394 kB JavaScript asset and one 125 kB CSS asset before compression. Feature route components are statically imported through the main application.
- **Impact:** The first usable desktop screen waits for editor, run-center, audit, workflow, and settings code that may not be needed in the current session.
- **Recommendation:** Introduce route-level dynamic imports after the shared-shell pass, while keeping the cockpit eagerly available.

### P2 — Component state vocabulary is encoded by selector exceptions

- **Location:** `frontend/src/styles/components.css`.
- **Category:** Accessibility / maintainability.
- **Evidence:** The base button selector relies on a growing exclusion list (`:not(.card):not(nav button):not(.voice)…`) and then several component classes override it with `!important`.
- **Impact:** Hover, disabled, danger, quiet and focus states are difficult to reason about and easy to make inaccessible when a new button class is added.
- **Recommendation:** Introduce explicit button variants (`primary`, `secondary`, `quiet`, `danger`, `icon`) with shared state rules; retain a single visible `:focus-visible` treatment.

### P3 — A stale monolithic stylesheet duplicates the actual imported system

- **Location:** `frontend/src/styles.css` and Python source-contract tests.
- **Category:** Maintainability.
- **Evidence:** The application imports `styles/index.css`; `styles.css` is not imported by the frontend but is still read directly by several tests. It mirrors old styles and increases the apparent stylesheet size by roughly 100 kB.
- **Impact:** Designers and engineers can change the rendered stylesheet while source-contract tests inspect a different one.
- **Recommendation:** Move the contract assertions to the true style entry/tokens and delete the stale duplicate after parity is verified.

## Positive findings to preserve

- The shell has a real skip link, semantic `nav` labels, `aria-current`, live busy feedback, and a strongly Chinese-first font stack.
- Visible keyboard focus and `prefers-reduced-motion` support already exist and should become centralized, not removed.
- The cockpit presents research status, blockers, evidence coverage and provenance as product content rather than developer-only diagnostics.
- The narrow palette and dark navigation rail are appropriate for a calm, professional research tool.

## Implementation sequence

1. **System foundation:** introduce semantic design tokens and a stable shared component vocabulary; reduce the cascade at the shell boundary.
2. **Shell redesign:** simplify orientation to one primary navigation system plus contextual page actions; improve hierarchy, spacing and responsive behaviour.
3. **Cockpit and shared surface pass:** make the next action, research health and evidence state scannable without visual clutter.
4. **Route-level hardening:** align feature pages, empty states, forms and tables to the new component states without touching the user’s in-progress research-map changes.
5. **Verification:** run typecheck, unit tests, production build and desktop/narrow smoke tests; audit the result again.
